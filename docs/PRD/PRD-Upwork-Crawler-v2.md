# PRD：NepTune Upwork 招聘线索抓取 v2（摘要模块）

本文档描述在 v1 基础上新增的 **摘要能力**，用于将职位完整描述压缩为 100 字以内的中文「核心描述」并展示在 Telegram 推送卡片中。当前实现使用**火山引擎 Doubao** 模型（如 Doubao-Seed-2.0-lite）。

---

## 一、与 v1 的关系

| 项目 | v1 | v2 |
|------|----|----|
| 抓取、存储、关键词、筛选 | 不变 | 不变 |
| 核心描述来源 | 描述正文前 30 字 | **大模型总结：完整描述 → 100 字以内中文**（当前为火山引擎 Doubao） |
| 推送卡片结构 | 不变 | 仅「🔍 核心描述」字段由摘要结果填充（若可用） |

v2 在**不改变现有抓取与入库逻辑**的前提下，在「抓取完成 → 推送 Telegram」之间增加一步：对每条待推送的 lead 调用摘要 API，用返回的中文摘要作为卡片中的「核心描述」。

---

## 二、产品目标（v2 新增）

- **目标**：利用大模型将 Upwork 职位**完整描述**总结为** 100 个中文字以内**的「核心描述」，在 Telegram 卡片中展示，便于快速判断需求要点，无需点开长文。当前使用火山引擎 Doubao 模型。
- **用户**：与 v1 一致（运营/招聘侧）；体验上获得更精炼、中文、可控字数的摘要。

---

## 三、功能范围（v2）

| 功能 | 说明 |
|------|------|
| 接入 | **火山引擎方舟 API**（Doubao 模型，如 `Doubao-Seed-2.0-lite`），仅用于文本总结。 |
| 输入 | 单条 lead 的 **description**（爬虫抓取的完整职位描述，已去 HTML）。 |
| 输出 | **100 字以内的中文**摘要，作为该条 lead 的「核心描述」用于推送。 |
| 触发时机 | 在 v1 流程中，**准备推送 Telegram 之前**：对本次要推送的每条 lead 调用一次摘要 API，得到摘要后写入该条 lead 的 `core_summary`，再走现有推送逻辑。 |
| 降级 | 未配置 `VOLCANO_API_KEY`、或调用失败/超时时：**回退为 v1 行为**，即「核心描述」仍为描述前 30 字，不阻塞推送。 |
| 存储（可选） | v2 最小范围为「推送时现场调用、不落库」。 |

---

## 四、交互流程（v2）

1. **沿用 v1**：抓取 → 去重 → 入库 → 得到本次待推送的 lead 列表。
2. **v2 新增**（在推送前）：
   - 若未配置 VOLCANO_API_KEY，则跳过本步，卡片「核心描述」用 description 前 30 字。
   - 若已配置：对每条待推送的 lead：
     - 取 `lead["description"]`（完整描述）；
     - 若描述为空或过短，可直接用前 30 字，不调 Gemini；
     - 否则调用摘要 API（火山引擎 Doubao），Prompt 约定见下节；
     - 将返回内容**截断/校验为 100 字以内中文**，写入该 lead 的展示用字段（如 `extra["core_summary"]` 或 `lead["core_summary"]`）；
     - 若调用失败或超时，该条使用 v1 规则（描述前 30 字）。
3. **推送**：按现有逻辑发送 Telegram，卡片中「🔍 核心描述」取 **摘要结果（若有）**，否则取描述前 30 字。

---

## 五、摘要 API 约定（当前实现）

- **服务**：火山引擎方舟 Responses API `https://ark.cn-beijing.volces.com/api/v3/responses`，模型由 `VOLCANO_MODEL` 指定（默认 `doubao-seed-2-0-lite-260215`）。
- **输入**：`messages` 含 system（总结规则）与 user（单条 lead 的 `description` 全文，截断至 6000 字）。
- **输出要求**（在 system prompt 中明确）：仅输出一段中文、100 字以内，概括职位需求要点；不要列表、标题或解释。
- **实现**：响应取 `choices[0].message.content`，做安全截断（100 字内）及空白清洗后写入卡片。

---

## 六、配置与安全（v2）

| 配置项 | 位置 | 必填 | 说明 |
|--------|------|------|------|
| VOLCANO_API_KEY | `.env` | v2 摘要功能启用时必填 | 火山引擎方舟 API 密钥；仅通过 .env 读取，不提交版本库。 |
| VOLCANO_MODEL | `.env` | 否 | 模型名称，默认 `doubao-seed-2-0-lite-260215`。 |

- **安全**：API Key 仅存在于本地 `.env`；`.env.example` 中仅写占位，不填真实 Key。

---

## 七、依赖与限制（v2）

- **依赖**：使用标准库 `urllib.request` 调用火山引擎 REST API，无额外第三方 SDK；Python 3.10+。
- **限流与成本**：每次推送 N 条即 N 次调用；请求超时 30s；描述送入前截断至 6000 字以控制 token。
- **语言**：Prompt 明确要求「仅输出中文、100 字以内」；若描述为多语言，由模型自行归纳为中文。

---

## 八、Telegram 卡片（v2）

- 卡片结构**与 v1 一致**，仅「🔍 核心描述」字段逻辑变化：
- **v2 且摘要 API 可用**：展示返回的 100 字以内中文摘要（`core_summary`）。
- **v2 但未配置/失败** 或 **未启用 v2**：展示 description 前 30 字（与 v1 一致）。

---

## 九、非目标（v2 不包含）

- 不改变 Apify 抓取、关键词、筛选、入库逻辑。
- 不做标题摘要、不做多轮对话、不做分类/打标签等其它 Gemini 能力。
- 不做「仅对部分 lead 调 Gemini」的复杂规则（v2 可简化为：凡推送且描述非空则调，失败则降级）。

---

## 十、文档与后续实现对应（建议）

- **v1 文档**：`docs/PRD/PRD-Upwork-Crawler-v1.md`（现有抓取、推送、配置）。
- **v2 实现**：
  - 摘要逻辑：`src/gemini_summary.py`（现为火山引擎 Doubao），负责「单条 description → 调用 API → 返回 100 字以内中文」；
  - 调用点：`src/run.py` 推送前调用 `enrich_leads_with_summary(all_leads)`；
  - 卡片数据：`format_lead_message` 优先使用 `lead.get("core_summary")` 或 `extra.get("core_summary")`，无则用 description 前 30 字。

---

## 十一、总结

v2 在 v1 基础上**仅增加「核心描述」的摘要能力**：抓取结果不变，在推送前对每条 lead 的完整描述调用火山引擎 Doubao，得到 100 字以内中文总结后填入 Telegram 卡片的「核心描述」；未配置或失败时回退为 v1 的「前 30 字」。配置项为 `.env` 中的 `VOLCANO_API_KEY` 与可选 `VOLCANO_MODEL`。
